# DATECS DP-150: ინტეგრაციის მოსამზადებელი ჩამონათვალი

**სტატუსი: Not integrated (Preparation only).** StorePOS V1.0 ფისკალურ აპარატთან კავშირს **არ ამყარებს**. ბრძანებას არ აგზავნის, COM პორტს არ ხსნის, „ფისკალურ ჩეკს“ არ აჩვენებს. ფისკალური ინტეგრაცია ცალკე ეტაპია.

ამ დოკუმენტში მხოლოდ ის არის, რაც უნდა გავარკვიოთ. Pinout, პროტოკოლის ბრძანებები, ბაუდის სიჩქარე და თავსებადობა **არ არის** მოყვანილი: მათ მწარმოებლის დოკუმენტი და მოწყობილობაზე შემოწმება განსაზღვრავს.

## 1. რა არის უკვე მზად კოდში

- `src/main/fiscal/fiscalPrinter.ts`: ინტერფეისი `FiscalPrinter` (`getStatus`, `printDocument`) და ერთადერთი იმპლემენტაცია `DisabledFiscalPrinter`. ის მხოლოდ აბრუნებს „არ არის დაკავშირებული“.
- ჩადებული წესები მომავალი დრაივერისთვის:
  - ჩეკი იბეჭდება **მხოლოდ** გაყიდვის/დაბრუნების ჩაწერის (SQLite commit) შემდეგ. პრინტერის შეცდომა ჩაწერილ გაყიდვას არ აუქმებს და არ აორმაგებს.
  - ერთ გაყიდვაზე/დაბრუნებაზე ერთი ფისკალური დოკუმენტი (უნიკალური ჩანაწერი). ხელახლა ცდა იმავე ჩანაწერს იყენებს, ორჯერ ვერ დაიბეჭდება.
  - წარუმატებელი ბეჭდვა რჩება „მოლოდინში“ და მეორდება მხოლოდ მომხმარებლის მოქმედებით, აუდიტში ჩაწერით.
  - თანხები მთელ თეთრებშია. მოწყობილობის ფორმატში გარდაქმნა მხოლოდ დრაივერის შიგნით ხდება.
- სხვა ფუნქციები ფისკალური აპარატის გარეშე მუშაობს.

## 2. მასალები, რომლებიც უკვე მიღებულია (ჯერ შეუმოწმებელი)

წინა ეტაპზე ნახსენები იყო: `KasaGE.dll`, SDK Sample, `KasaGE.xml`, DP-25 პროტოკოლის PDF. ისინი ამ რეპოზიტორიაში **არ არის** და მათი შინაარსი არ შემიმოწმებია. ინტეგრაციის დაწყებამდე საჭიროა მათი ასლი (არა GitHub-ზე: ლიცენზია შეიძლება ზღუდავდეს გავრცელებას).

## 3. რა უნდა გავარკვიოთ მწარმოებელთან / მომწოდებელთან (Kasa.ge ან DATECS-ის ავტორიზებული სერვისი)

### აპარატი
- [ ] ზუსტი მოდელი და მოდიფიკაცია (DP-150 / DP-150 KL / სხვა), **firmware-ის ვერსია**, ქვეყნის (საქართველოს) ვერსია.
- [ ] აქვს თუ არა აპარატს **PC-დან მართვის რეჟიმი** („fiscal printer mode“ / კომპიუტერთან მიერთება) და როგორ ირთვება.
- [ ] საჭიროა თუ არა ამისთვის სერვისის მიერ აპარატის გადაკონფიგურირება ან ლიცენზია. ვის აქვს ამის უფლება.

### SDK და პროტოკოლი
- [ ] **წერილობითი დადასტურება**, რომ `KasaGE.dll` / DP-25 პროტოკოლი მოქმედებს **DP-150**-ზე, ამ firmware-ით.
- [ ] SDK-ის ვერსია, .NET ვერსიის მოთხოვნა (.NET Framework/.NET), 32 თუ 64 ბიტი, ლიცენზიის პირობები (დაშვებულია თუ არა პროგრამასთან ერთად გავრცელება).
- [ ] ბრძანებების სრული სია ჩვენი ოპერაციებისთვის: ჩეკის გახსნა, პოზიცია, ფასდაკლება, გადახდა (ნაღდი / სხვა), ჩეკის დახურვა, ჩეკის გაუქმება, დაბრუნების (refund/storno) ჩეკი, X-ანგარიში, Z-ანგარიში, სტატუსი, ქაღალდის დასრულება, შეცდომების კოდები.
- [ ] დღგ-ის/საგადასახადო ჯგუფები: რომელი ჯგუფი გამოიყენება ჩვენს საქონელზე.
- [ ] ქართული ტექსტის კოდირება ჩეკზე, ხაზის მაქსიმალური სიგრძე, დასახელების სიგრძე.
- [ ] დამრგვალების წესი და თანხის ფორმატი (თეთრი/ლარი).
- [ ] ოპერატორის/მოლარის კოდი და პაროლი: როგორ ენიჭება და სად ინახება (ჩვენთან ბაზაში ღია ტექსტით არ შეინახება).
- [ ] **სატესტო/სასწავლო რეჟიმი**, რომელიც ფისკალურ მეხსიერებაში არაფერს წერს. აუცილებელია პირველი ტესტებისთვის.

### კავშირი
- [ ] რომელი პორტით უერთდება კომპიუტერს: RS-232, USB (ვირტუალური COM), Bluetooth, LAN.
- [ ] **ორიგინალი კაბელის** ტიპი და კოდი მწარმოებლისგან. Pinout-ს ჩვენ არ ვიგონებთ. თუ საჭიროა USB→RS-232 ადაპტერი, რომელი ჩიპით (მაგ. მწარმოებლის რეკომენდაცია) და დრაივერი.
- [ ] COM პარამეტრები **მწარმოებლის დოკუმენტიდან**: სიჩქარე (baud), data bits, parity, stop bits, flow control, timeout-ები.

### იურიდიული და ბუღალტრული
- [ ] შემოსავლების სამსახურის მოთხოვნები PC-დან მართულ ფისკალურ აპარატზე: რეგისტრაცია, შეტყობინება, დაშვებული მოდელები.
- [ ] ნისიით, შერეული გადახდით და გაცვლით გაყიდვის ფისკალური ასახვის წესი (რა იბეჭდება და როდის): ბუღალტერთან და მომწოდებელთან.
- [ ] Z-ანგარიშის ვალდებულება (24 საათში) და რა ხდება, თუ დღის ბოლოს Z არ გაკეთდა.
- [ ] აპარატის გაუმართაობისას რა უნდა მოიმოქმედოს მაღაზიამ (კანონით).

## 4. COM/Serial პარამეტრების დადგენის პროცესი (ბრძანებების გაგზავნის გარეშე)

1. აპარატი ჩართე ჩვეულებრივ რეჟიმში. კომპიუტერს მიუერთე **მწარმოებლის** კაბელით.
2. Windows → **Device Manager** → „Ports (COM & LPT)“. ჩაიწერე, რომელი COM ნომერი გაჩნდა მიერთებისას და გაქრა გამორთვისას. ჩაიწერე მოწყობილობის სახელი/ჩიპი.
3. თუ ახალი პორტი არ ჩანს: საჭიროა USB-serial ადაპტერის დრაივერი (მხოლოდ მწარმოებლის საიტიდან). ან აპარატი სხვა ინტერფეისით უერთდება.
4. სიჩქარე და სხვა პარამეტრები აიღე **მწარმოებლის დოკუმენტიდან** ან აპარატის სერვისის მენიუდან (თუ ჩანს). შემთხვევითი ცდებით არ ვარჩევთ.
5. პირველი კავშირი: **მხოლოდ მწარმოებლის ოფიციალური სატესტო პროგრამით ან SDK Sample-ით**, მხოლოდ **სტატუსის წაკითხვის** ბრძანებით და სატესტო რეჟიმში. ჩეკის ბრძანება ამ ეტაპზე არ იგზავნება.
6. ჩაწერე შედეგი: COM ნომერი, პარამეტრები, SDK/firmware ვერსიები, სტატუსის პასუხი, ეკრანის სურათები.

## 5. ინტეგრაციის ეტაპები (როცა §3 და §4 დასრულდება)

1. მცირე დამოუკიდებელი .NET პროცესი: მხოლოდ `KasaGE.dll` + `FiscalPrinter` ინტერფეისის ბრძანებები, StorePOS-თან JSON-ით (stdin/stdout). main process-ში native კოდი არ იტვირთება.
2. სატესტო რეჟიმში: სტატუსი → X-ანგარიში → ერთი ჩეკი → დაბრუნების ჩეკი → შეცდომების იმიტაცია (ქაღალდი, კაბელის გამოძრობა) → ხელახლა ცდა ორმაგი ბეჭდვის გარეშე.
3. „მოლოდინში“ ჩეკების სია და ხელით ხელახლა ბეჭდვა StorePOS-ში, აუდიტით.
4. რეალურ რეჟიმში: ერთი ჩეკი და Z-ანგარიში, ბუღალტერთან ერთად.
5. მხოლოდ ამის შემდეგ ირთვება ავტომატური ბეჭდვა გაყიდვისას.

## 6. რასაც არ ვაკეთებთ

- ბრძანებებს, pinout-ს ან პარამეტრებს არ ვიგონებთ.
- დაუდასტურებელ მოწყობილობაზე ფისკალურ ბრძანებას არ ვაგზავნით.
- არ ვამატებთ „Dummy“ ფისკალურ ჩეკს, რომელიც რეალურ ფისკალურ ჩეკად გამოჩნდება. StorePOS-ის ჩეკი ფისკალური **არ არის**.
