# Security Validation Report — StorePOS V1.0

კოდი: `c825b1b`. ტესტები: `src/main/ipc/security.test.ts` (6 სცენარი რეალური IPC dispatcher-ით), `e2e/desktop-acceptance.mjs` (დაყენებულ პროგრამაზე).

## 1. როლები და სერვერის მხარის შემოწმება

ყველა IPC არხს (`src/main/ipc/handlers.ts`) აქვს წვდომის დონე: `public` (მხოლოდ შესვლამდე საჭირო 5 არხი), `user` (ნებისმიერი შესული მომხმარებელი) ან `owner`. შემოწმება ხდება main process-ში, UI-ის დამალვაზე დამოუკიდებლად.

| მოქმედება | Owner | Seller |
|---|---|---|
| გაყიდვა, ნისიით/შერეული გაყიდვა, კლიენტის რეგისტრაცია, ნისიის დაფარვა | ✅ | ✅ |
| დაბრუნება/გაცვლა ისტორიიდან, პროდუქტის ძებნა, ისტორიის ნახვა | ✅ | ✅ |
| პროდუქტის შექმნა/რედაქტირება/არქივი, ფოტოები, კატეგორიები | ✅ | ❌ |
| ფასდაკლება (პოზიციაზე/კალათაზე), ფასის ცვლილება | ✅ | ❌ (სერვერი უარყოფს) |
| მარაგის შევსება/კორექცია | ✅ | ❌ |
| ფინანსები, ხარჯები, CSV | ✅ | ❌ |

**მონაცემთა ფილტრი:** Seller-ის ყოველ პასუხს main process აშორებს ველებს, რომელთა სახელი შეიცავს `cost`, `profit` ან `cogs`-ს (თვითღირებულება, FIFO ფენები, მოგება) — ნებისმიერ არხზე, მომავალში დამატებულზეც. `pin_hash`/`pin_salt` არცერთ პასუხში არ ხვდება.

დადასტურება: Seller-ის 9 სხვადასხვა პასუხში (კატალოგი, ძებნა კოდით, ჩეკი, ისტორია, დაბრუნებები, მოძრაობები, აქტიური ნისიები) მგრძნობიარე ველი 0; 15 owner-ის არხი Seller-ისთვის უარყოფილია; უცნობი არხი, `__proto__` და არასწორი payload — უარყოფილი.

## 2. PIN და სესიები

- PIN: 4–6 ციფრი, PBKDF2-HMAC-SHA256, 120 000 iteration, 16-ბაიტიანი salt, `timingSafeEqual`. ძველი (10 000) ჰეშები მუშაობს და შესვლისას ახლდება (upgrade ტესტით დადასტურდა).
- **Lockout:** 4 არასწორი მცდელობის შემდეგ ანგარიში იბლოკება 30 წმ, შემდეგ 1, 2, 5, 15 წუთით. მრიცხველი SQLite-შია — პროგრამის გადატვირთვა მას არ ანულებს. Owner-ს შეუძლია განბლოკვა.
- სესია: 256-ბიტიანი შემთხვევითი token, მხოლოდ მეხსიერებაში; ვადა — 60 წთ უმოქმედობა ან 16 საათი; ყოველ მოთხოვნაზე მოწმდება, რომ მომხმარებელი ჯერ კიდევ აქტიურია და როლი არ შეცვლილა.
- სესია უქმდება: ჩაკეტვისას (F12 / ავტომატური), დაბლოკვისას, PIN-ის განულებისას, PIN-ის შეცვლისას (სხვა სესიები), Restore-ის შემდეგ, პროგრამის დახურვისას.
- PIN-ს ვერავინ ნახულობს. Owner ანულებს თანამშრომლის PIN-ს ძველის ნახვის გარეშე; საკუთარი PIN-ის შეცვლა მოითხოვს მიმდინარე PIN-ს.
- წაიშალა: Login-ის ღილაკი „საწყისი PIN: 1234“ და შეცდომის ტექსტი „(საწყისი PIN: 1234)“.

## 4. რას ვერ იცავს PIN

ბაზა ინახება `%APPDATA%\StorePOS\data\store.db`-ში. ვისაც Windows-ის ანგარიშზე/დისკზე სრული წვდომა აქვს, შეუძლია ფაილის კოპირება; 4–6 ციფრიანი PIN-ის ჰეში ასლზე offline შერჩევით გაიხსნება. რეკომენდაციები:

1. Windows-ის ანგარიშზე პაროლი და ეკრანის ავტომატური ჩაკეტვა.
2. BitLocker (Windows Pro) დისკზე.
3. Backup-ის USB ინახებოდეს დაცულ ადგილას — `.posbackup` ფაილი დაშიფრული არ არის.
4. Seller-ებს Windows-ის ადმინისტრატორის უფლება არ ჰქონდეთ.

## 5. ცნობილი შეზღუდვები

- ინსტალერი და `StorePOS.exe` ციფრული ხელმოწერის გარეშეა (code signing სერტიფიკატი არ არის).
- `.posbackup` შეიცავს ბაზას დაშიფვრის გარეშე.
- Git-ის ისტორიაში რჩება AI Studio-ს სატესტო ბაზა Owner-ის PIN ჰეშით (იხ. RELEASE_READINESS §7).
