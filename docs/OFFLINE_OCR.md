# StorePOS: ხელნაწერი 5-ნიშნა კოდის offline ამოცნობა (OCR), RC3

**სტატუსი:** Software Verified / Hardware Pending. RC3-ში ამოცნობა თავიდან აიწყო. სიმულირებულ ფოტოებზე, რომლებიც ნამდვილი ხელწერისგან (44 ადამიანი) არის შექმნილი, შედეგები §6-შია. **რეალური ვებკამერით, შენი ფურცლით და ხელწერით სიზუსტე ჯერ გაზომილი არ არის:** [hardware/OCR_FIELD_TEST_KA.md](hardware/OCR_FIELD_TEST_KA.md).

## 1. დანიშნულება და პრინციპები

მფლობელი ქარხნული შტრიხკოდის არმქონე პროდუქტს ხელით ანიჭებს 5-ნიშნა კოდს (10000–99999). გამყიდველს ეს კოდი კამერით შეუძლია წაიკითხოს.

- **მთლიანად offline.** მოდელი პროგრამაშია, ინტერნეტი და გარე API არ გამოიყენება.
- **შედეგი ავტომატურად კალათაში არასდროს ემატება.** კამერა იღებს კადრს → OCR ცდილობს ამოცნობას → გამყიდველი ხედავს კოდს და საეჭვო ციფრებს → საჭიროებისას ასწორებს → პროგრამა პოულობს პროდუქტს (სახელი, ვარიანტი, ფასი, მარაგი) → გამყიდველი ადასტურებს.
- **ციფრი არ გამოიგონება.** რასაც მოდელი ვერ კითხულობს, ცარიელი რჩება. თუ ზუსტად 5 სიმბოლო ვერ მოიძებნა, კოდი უარყოფილია და მიზეზი ჩანს. ბაზაში არსებულ კოდთან შემთხვევით დამთხვევა ამოცნობის სისწორედ არ ითვლება და სანდოობას არ ზრდის.

## 3. ახალი დამუშავება (`src/main/ocr/`)

→ მელნის სიმუქე 0..1
→ ჰისტერეზისის ზღვარი (მუქი ბირთვი + მისი მკრთალი გაგრძელება; მკრთალი ცალკე ლაქა იყრება)

→ კოდის ხაზი: მსგავსი სიმაღლის სიმბოლოები ერთ დონეზე
→ ზუსტად 5: ზედმეტი (კიდესთან მოჭრილი, პატარა ლაქა) იყრება; შეხებული ციფრები იჭრება

**გადაწყვეტილებები ციფრზე** (`engine.ts`):
- p ≥ 98%: ჩვეულებრივი.
- 50% ≤ p < 98%: ციფრი ჩანს, **ყვითლად მონიშნული**. ზღვარი სავალიდაციო ავტორებზე შეირჩა (არც სწავლებაში, არც ტესტში არ ყოფილან): 98%-ზე მონიშვნის გარეშე არასწორი კოდი 0.7%-ია (85%-ზე 2.4% იყო), სწორი კოდების 15% კი შესამოწმებლად ინიშნება.
- p < 50%: უჯრა **ცარიელია**, მონიშნული. გამყიდველი თავად წერს.
- პირველი ციფრი „0“: ყოველთვის მონიშნული (კოდები 10000-დან იწყება).
- ჩარჩოს კიდეს შეხებული ციფრი: მონიშნული (შეიძლება მოჭრილი იყოს).
- შეხებული ხელწერიდან ამოჭრილი ციფრი: ყოველთვის მონიშნული (არასწორი ჭრილიც შეიძლება მოდელს დამაჯერებელ ციფრად მოეჩვენოს).

**უარყოფის მიზეზები:** ჩარჩოში არაფერია (`no_ink`); მკრთალია (`low_contrast`); 5-ზე ნაკლები (`too_few`, „ვიპოვე N სიმბოლო“); 5-ზე მეტი (`too_many`); ძალიან პატარა, ციფრი < 20 px (`too_small`); კიდეს ეხება ან ჩარჩოს გარეთაა (`border`).

**სანდოობის პროცენტი** ნიშნავს მოდელის შეფასებას, რომ მთელი კოდი სწორია (5 ციფრის ალბათობების ნამრავლი). ალბათობები კალიბრირებულია სავალიდაციო მონაცემებზე (temperature scaling). ეს **სიმულირებულ** ფოტოებზეა მორგებული; რეალურ ფოტოებზე კალიბრაცია საველე ტესტით შემოწმდება.

**რატომ არა მთლიანი თანმიმდევრობის ამოცნობა (CRNN/CTC):** კოდი ყოველთვის 5 ციფრია და ჩვეულებრივ ცალ-ცალკე იწერება. ციფრების ცალ-ცალკე ამოცნობა თითო პოზიციას საკუთარ ალბათობას აძლევს, და ეს სალაროს უსაფრთხო პროცესს სჭირდება: საეჭვო ციფრის მონიშვნა, ცარიელი უჯრა, კიდესთან მოჭრილი ციფრი. თითო ციფრი დიაგნოსტიკაშიც ჩანს. სასწავლო მონაცემები (ცალკეული ციფრები, ლიცენზიით) საკმარისია. შეხებული ციფრებისთვის ჭრა თვითონ მოდელის შეფასებით ირჩევა, რაც თანმიმდევრობის დეკოდირების მსუბუქი ფორმაა. თუ რეალური ნიმუშები აჩვენებს, რომ შეხებული ხელწერა ხშირია და ჭრა საკმარისი არ არის, თანმიმდევრობის მოდელი შემდეგი ნაბიჯი იქნება.

## 4. სად სრულდება

- Renderer: მხოლოდ კადრის ამოჭრა და პიქსელების გაგზავნა (`ocr:recognize`, typed array). main process ზომას და სიგრძეს ამოწმებს.
- Main process → **ცალკე ნაკადი** (`worker_threads`, `dist-electron/ocrWorker.cjs`). ფანჯარა და ბაზა OCR-ს არ ელოდება. თუ ნაკადი 15 წამში ვერ დაასრულებს, ჩერდება და შემდეგი ცდა ახალ ნაკადს იწყებს. თუ ნაკადი ვერ ჩაიტვირთა, იგივე კოდი main process-ში სრულდება (`ranOn: 'main'`, დიაგნოსტიკაში ჩანს).
- მოდელი იტვირთება კამერის ფანჯრის გახსნისას (`ocr:isModelReady`), რომ პირველი ამოცნობა არ დაელოდოს.
- onnxruntime-web, WASM, ერთი ნაკადი.

- დრო (i7-7700): p50 118 მს, p95 356 მს.
- **რეალური ვებკამერით ჯერ არ გაზომილა.**
